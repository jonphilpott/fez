# FEZ: Personal Sound Computer (C, SDL2)

Tag line: "a forth programmable virtual analog synth engine". The project is called FEZ; "Personal Sound Computer" is its descriptor (decided 25 Nov 2026). It began as a C64-style register synth.

FEZ is the project's name (F is for Forth; the backronym for E and Z is still undecided). 


**Requirement: the code must be easily maintainable by humans, not just by agents.** Plain, boring, well-commented code; one definition of each thing; no clever tricks. Comments teach a junior developer new to DSP and C++ (the why and how, numbered steps in long functions). Minimal libraries: plain C99, SDL2 only for the apps.

## What this is

A SID-style register synthesiser with a Forth-like token VM, a Buchla/Music Easel-style voice (vactrol lowpass gate, Moog-style ladder for the mod voice), four pulsers, a modulation matrix and virtual devices (cellular automaton, Lorenz attractor, 8-step sequencer, quantiser, Turing machine, keyboard, buffer device with grains), and a serial effects chain (tape delay, spring, compressor). The core is portable C with no malloc or OS calls. It began as a JavaScript prototype (no longer in this repo); comments that say "the JS" mean that reference.

Targets: the desktop app (macOS, Linux; works now), a Raspberry Pi build of the same (HDMI screen 1024x600, USB keyboard, custom MIDI controller with 32 fixed-CC pots), the TrimUI Brick handheld (256x192 logical screen at 4x; `fez --brick`), and later an STM32H743 (Daisy-class).

## Layout

    core/       portable C core: fez.h (the one public header), vm.c, words.c (what each VM word does: stack picture and a sentence, one row per operation, a test keeps it in step with `OP_NAMES`), regs.c, synth.c, devices.c, buf.c, audio.c (voice, effects),
                filters.c, scales.c; tables.c (parameters, names, help, example patches: edited by hand) and reg_names.h (the register map);
                regview.c (how registers are listed, formatted, edited), palette.c and patchfile.c (a whole patch as text and back; no file calls) are shared by both UIs
    desk/       the DESKTOP app (`fez`): keyboard-driven, window split into tiles with tabs (editor, patches, pulsers, seq, matrix,
                devices (pages: cellular, lorenz, quantiser, turing, delay, keys), buffer (pages: tape, voices), ctrl (every register in one list under
                group headings; Tab switches units and raw numbers; the master volume LEVEL is its first row), scope), 3 layouts named 1 to 3 (1: editor, scope, ctrl; 2: a 50/50 split of editor and ctrl; 3: scope strip over ctrl and devices); the editor keeps its own
                text per block and applies on Ctrl+Enter; gfx.c draws into a pixel array, main.c is the only SDL file;
                userpatch.c is the only patch disk code, wavrec.c the only recording disk code
                pad.c (the handheld's controls: buttons to keys, menu, palette of words for the editor, patch-name letter picker, button help; no typing needed), tab_play.c (four pads that fire the pulsers by hand)
    test/       test_core.c (tables) and test_patchfile.c (every example patch survives a write and read back). The old golden-vector tests against the JS were dropped.
    docs/       the manual: template.html, style.css, chapters/*.html (hand-written prose); manual.html is GENERATED, do not edit it
    tools/      render.c offline renderer (WAV output, level check, 100 percent feedback stress test), deskshot.c and padshot.c (draw the desktop layouts / every handheld screen to PPM without a window), manual.c (builds docs/manual.html)

## The handheld (TrimUI Brick)

`fez --brick` is the same program with a fixed 256x192 picture, one full-screen tile (layout HAND) at text scale 1, and a `Pad` (desk/pad.c) in front of the keys. A first-class instrument minus the keyboard: every desktop screen is on it, because it IS the desktop UI. A fix to a desktop tab is a fix to the handheld. The tab order (EDITOR, PATCHES, CTRL, DEVICES, BUFFER, PULSERS, SEQ, MATRIX, PLAY, SCOPE) is the one enum in desk.h and serves both.
- L1 / R1 change screen (Ctrl+[ ]); L2 / R2 change page inside a screen (plain [ ]); D-pad moves; Y held is Shift (coarse steps, select); Start fires the gate; Select mutes; Menu opens the menu (screen actions, go to screen, record, pulsers, button help, quit); Vol +/- is the master level.
- A, B, X depend on the screen (see `screen_key` and `tab_hint` in pad.c; the hints are shown in the status bar). Editor: A opens the palette of words (its REGS tab is sectioned under the same headings as CTRL, built from CTRL's own row list), numbers from NUMS glue together and ENT ends one, B deletes a word, X applies the block. Patches: A loads, X saves (letter picker: Up/Down letter, Left/Right five letters, A adds, B deletes, X saves, Y cancels), B deletes. CTRL: A/B step up/down, X units/raw. PLAY: A B X Y fire pulsers P0 to P3.
- The handheld Menu has two tabs, the screen's own (named like the tab bar, e.g. EDITOR; the current screen's actions; the menu opens here when the screen has any) and MENU (new blank patch, go to screen, record, pulsers, help, quit, close); Left/Right or L1/R1 switch. B closes, except inside Go to screen where it goes back to MENU.
- The editor's own tab has four checkboxes, `[x] Runs on P0` to `P3` (the block's BP# mask): A toggles one and the menu stays open. Anything a key did that no button reaches is in the Menu's first tab (a table per tab in pad.c, each entry a key the desktop tab already understands). No typing of numbers yet: Left/Right with Y held covers the range.
- Keyboard stand-in (main.c `key_to_button`): arrows, X Z = A B, S A = X Y, Q W = L1 R1, E R = L2 R2, Return = Start, Shift = Select, Esc = Menu, - = Vol-, = Vol+. A game controller works too (`controller_to_button`).
- `desk.handheld` shortens the status bar and swaps a few key-name hints for button ones; `desk.hint_override` carries the pad's hints.
- The DEVICES pages start with DELAY: DELAY, CELLULAR, LORENZ, QUANTISER, TURING, KEYS.

### Getting it onto the Brick

`brick/build.sh` (needs Docker; Colima works) pulls LoveRetro's published `ghcr.io/loveretro/tg5040-toolchain` image (an aarch64 gcc 8.3 plus the Brick's own SDL2 2.26, from the Trimui SDK; building the image from its Dockerfile failed in an unrelated library), runs `make brick` inside it, and lays out two paks in `dist/`: `FEZ-probe.pak` (a small program that reports the device's SDL drivers, screen, audio and button numbers, and plays a tone; its report goes to `probe.log` in the pak folder) and `FEZ.pak` (the app; log in `fez.log`; `HOME` is set to the card so patches and recordings land in `FEZ/` on it). Copy a pak folder to `Tools/tg5040/` on the card of a NextUI or MinUI install. Run the probe first. The cross-build works (25 Nov 2026: aarch64 ELF binaries needing only libSDL2, libm and libc, GLIBC 2.17 at most; a harmless RUNPATH points at a container path). Nothing has been run on a Brick yet (the files are written from the documentation: a pak is a folder with a `launch.sh`), so the first run is where the guesses get tested.

## Build and test (from the repo root)

    make test            # builds and runs the tests; must end "all tests ok"
    make && ./fez        # desktop app (needs SDL2: brew install sdl2, or apt install libsdl2-dev)
    ./fez --brick        # the handheld UI (256x192, scaled up) on the desktop; the keyboard stands in for the buttons
    make render && ./render all     # peak and RMS of every example patch (NaN, silence and runaway feedback show here)
    make deskshot / make padshot    # screens to .ppm files
    make manual                     # docs/manual.html from docs/ and the tables (words.c, tables.c, palette.c)

Compile with `-ffp-contract=off` (the Makefile does): fused multiply-add changes the Lorenz results and filters between machines. The sound itself can only be judged by ear: `render` catches silence, clipping, NaN and runaway feedback, nothing more.

## Using the desktop app

Files: one visible folder, `~/FEZ/`, with `patches/` (text files `<name>.fez`) and `recordings/` (WAV takes). On first run with a new `~/FEZ/patches/`, patches from the old hidden folder (`~/Library/Application Support/fez/patches/` on macOS, `~/.local/share/fez/patches/` on Linux) are copied in, and the old files are left alone. On Windows (cross-built with MinGW: `make win-zip`) it is `%USERPROFILE%\\FEZ\\`. On iOS (built by a separate wrapper project, not in this repo) the folder is `Documents/FEZ/` inside the app, so the Files app can show it (`#ifdef __IPHONEOS__` in desk/main.c). The app starts from a blank patch. Patches tab: Left/Right switch MY PATCHES (the default) and EXAMPLES (built in), typing filters, Enter loads, Ctrl+S saves (always asks for a name), Ctrl+N starts a blank patch (asks first, in a centred dialog on the handheld (`draw_confirm` in pad.c: A Yes, B No, also used for delete and overwrite) and a text line on the desktop, `PAT_CONFIRM_NEW`; on the handheld it is a row in the Menu and in the Patches screen's own tab), Ctrl+D or Delete deletes. No autosave, by decision. The buffer audio is not saved. Loading a patch clears the buffer, the delay, the spring and the compressor.

Keys: plain `[` and `]` move to the previous or next page inside a tab (editor blocks, Patches lists, Devices pages); Ctrl or Alt with them change the tab, so the editor cannot type brackets. Ctrl (or Alt) + arrows move between tiles, Ctrl+Tab next layout, Ctrl+= / Ctrl+- text size, Ctrl+G gate, Ctrl+P pulsers, Ctrl+F full screen, Ctrl+Q quit, F1 the help page (a full-window overlay from `desk/help.c`, two plain text tables; it swallows every key except F1 and Esc, which close it, and Shift+Esc mute; keep it in step when keys change), Ctrl+S save, Ctrl+T start/stop a recording (the final output, after mute, as a 24-bit stereo WAV at the synth rate, named `<date>_<time>_<patch>.wav`; Ctrl+R is the editor's run-block, so it was not free), Shift+Esc global mute (a 20 ms fade of the output; the synth keeps running; plain Esc still cancels entries). No Home/End/Page keys: it must be fast on a laptop. Target screen 1024x600 (the Pi LCD). The CTRL list's group headings come from the `GROUPS` table in `desk/tab_values.c` (each starts at a register constant); a new device group needs one line there.

Colours: one table, `core/palette.c`, shared by both UIs; a high-contrast scheme on pure black. Each ink has one job: amber (gold) is selection and the write head, cyan register names and waveforms, green notes and on-states, red errors, and magenta (`COL_MAG`) is movement: modulation (the "now" values and ticks), playheads, grain voices, pulser activity, held keys and the CTRL group headings.

Status bar, right end: a CPU load bar labelled CPU (how long the audio callback takes, as a share of the time its buffer lasts; the bar is a smoothed average, the thin marker is the worst buffer of the last 3 s; green below 70 percent, amber to 90, red above) and a red CLIP flag that shows for a second after the output reaches full scale. It replaced the old level meter; the scope header still prints the peak. Measured on an Apple laptop: every example patch uses about 0.5 to 1 percent.

Recording: the audio thread never touches the disk. It drops each output sample into a ring buffer (`rec_ring` in `main.c`) and the main loop empties it into the WAV file.

## Things that are true and easy to get wrong

- **The register map is grouped, and code never writes a bare address.** Each device owns one unbroken run of addresses (voice 100-110 with the complex oscillator's CXWAVE and CXBLEND and GATE, CV 111-114, mixer 115-119 ending in LEVEL, pots, mod voice, delay and spring 129-139, slew, cellular 400s, Lorenz, sequencer, buffer, grains, pulsers 510-526, quantiser, Turing, keyboard 550-553). Addresses are written once, in `core/reg_names.h`; everything else uses names (`REG_DLYTIME`), including the tables and the example patches in `tables.c`, so regrouping the map is one edit there. To add a register, give it the next free address in its group, or open a new group, then add it to `NAME_TABLE` (and `PARAM_TABLE`, `HELP_TABLE`) in `core/tables.c`. Saved patches and the example patches store names, so moving a register does not break them.
- **The tables are the single source of truth.** Names, parameter defaults and ranges, one-line help for the small screens (49 characters max; a test enforces it) and the example patches are all in `tables.c`.
- **Quantiser and Turing machine** (registers QON to QROOT and TMPUL to TMOUT, matrix source 20 `TM`): the quantiser snaps the *effective* pitch (`eff[PITCH]`, after the matrix), never the PITCH register. `TMBITS` is the one register that lives outside the register file (`tm.bits`); `patchfile.c` special-cases it. The Turing machine uses one random number per step, always.
- **The effects chain is in series**: voice, mod voice and the buffer's return (MIXBF) go into the tape delay, its output into the spring, that into the compressor. **The spring is stereo and is the only stereo part**: two tanks (left 34 ms, right 41 ms, different allpass tunings), both fed from the delay's output, each also fed 30 percent of the other's output (`SPR_CROSS` in `audio.c`; stable at full feedback). SPRWID (0 to full, default 0, so existing patches stay mono until you open it) blends the two outputs by mid and side: 0 gives the same signal in both ears (exactly mono), full gives each ear its own tank. The compressor has one detector (the louder ear) and one gain, so it never shifts the image. The core renders with `fez_render_stereo` (interleaved left, right); `fez_render` is the mono mix `(L+R)/2` for tools. The scope draws two lanes, left (green) above right (cyan), both starting at a rising crossing found in the left channel; its ring is interleaved stereo (`d->scope` holds 2 * `SCOPE_RING` floats). The meters follow the louder ear, and recordings are true stereo. Tests: `test/test_audio.c`. The tape delay (DLYTIME 0 to 12 s, linear, 0.37 ms a step, a 2.3 MB ring; the buffer device runs up to 30 s, 5.8 MB; both are fixed arrays in `audio.h` and `buf.h`) has DLYFB (0 to 100 percent, no cap), DLYMIX (a true dry/wet crossfade: full means loop only), DLYIN (how much sound is written into the loop, squared curve, default full; 0 closes the loop), DLYLP (feedback lowpass, 300 Hz to 12 kHz), DLYWOB (wow and flutter), DLYNZ (hiss written into the loop) and DLYFRZ (freeze at or above 16384; blends the loop to an exact copy). Tested at maximum settings: bounded, and a frozen loop does not fade. DLYTIME 0 is a comb filter, not an echo.
- **Keyboard device** (registers KBNOTE, KBGATE read only, KBOCT, KBPUL; matrix source 21 `KB`, ROUTE takes KBNOTE as its source): `fez_note_on/off/all_notes_off` in `synth.c` is the one place notes enter, and where MIDI will land. A key down writes PITCH and KBNOTE, fires the envelope and fires the KBPUL pulsers; newest key wins, and letting go of it returns to the one before with no new trigger. **Sustain**: `gate_hold` (set while any key is down) keeps the control envelope at the top and the audio lowpass gate's LED on; the last key up lets it fall over REL. Blocks, pulsers and the sequencer still fire the old trigger envelope. On the desktop the KEYS page plays the tracker layout (Z S X D C V G B H N J M, then Q 2 W 3 E R 5 T 6 Y 7 U, by scancode so any keyboard layout works); only that page plays, but a key-up is always honoured, and losing window focus lets go of everything.
- - **GATELEVEL** (register 111, in the voice run after GATE; CV0 to LEVEL moved up one to make room): the lowpass gate's opening is `clamp(vactrol + GATELEVEL / 32767, 0, 1)` in `audio.c`. 0 (the default) is the old behaviour; full is an always-open gate (a drone). It is a normal parameter, so the matrix can modulate it. ENV (the matrix source) stays the pure envelope.
**Pitch is 8.8 semitones**: MIDI note x 256 (C4 = 15360, octave = 3072). `ST` converts semitones, `HZ` converts tenths of a hertz (4400 HZ = A4). Registers hold 0 to 32767; literals are 15 bit and have no sign: a negative number is written `5 NEG`, On the handheld the editor's own tab has Copy, Cut and Paste (Ctrl+C/X/V in the desktop editor); select with Y held and the D-pad, and B deletes a selection instead of a word. On the handheld the two analogue sticks are MP0..MP3 on every screen (`pad_stick` in `desk/pad.c`: centre 16384, a dead zone of 4096 raw, up raises the pot; the Devices screen has no KEYS page, by Jon's decision 25 Nov 2026: playing notes needs a keyboard). A patch load leaves the pots alone (they are the controls, not the patch). The 16 modulation pots MP0..MP15 are read-only to code and set by the host with `fez_set_pot` (MIDI will use it); they live at addresses 560 to 575 (MP0..MP3 used to be at 120..123, now unused), and as matrix sources they are 7..22 in one run (the sources are numbered in `SRC_NAMES`: none, LFO0, ENV, CV0..3, MP0..15, CADENS, SLO0..3, LZX..LZZ, SQ, TM, KB = 0..33). Patch files store routes by source NAME (`route ENV CUTOFF 6000`), so renumbering sources cannot break a saved patch (old numeric `route 2 ...` lines are skipped and counted; Jon chose a clean format over compatibility, 25 Nov 2026). The built-in examples in `tables.c` still hold source numbers, so renumber those by hand if the sources ever move. `*` multiplies whole numbers (saturating, like `+`) and `F*` multiplies fractions (32768 is 1.0; this was `*` until 25 Nov 2026, when Jon asked for consistency; nothing used it), and a typed `-5` is a compile error ("no negative numbers: write 5 NEG"), so every token is exactly one slot and SKIP skips exactly one visible token (changed 25 Nov 2026; no example or saved patch used a negative literal). Block size is 128 slots.
- **Pulsers hold no block.** Each block has a 4-bit pulser mask (BP0 to BP15); SQPUL and GRPUL are masks for the sequencer clock and the next grain; RUN runs a block next tick. A block runs once per tick however many pulsers fire.
- **Pulser rate** is pulses per minute, 10 minimum (a file load clamps lower rates to 10, so patches use probabilistic blocks for slow events).
- **Low-passed white noise is very quiet.** The mod voice noise feed (`MDNZ`) is lifted by sqrt(8000 / cutoff Hz), limited to 1..6, to keep sweeps at a steady loudness.
- **Envelope times**: ATK is 1 ms to 500 ms and REL is 10 ms to 4 s on log scales, so register values such as 12000 are short. Patches with "slow" notes need values above 20000.
- **LEVEL** (the master volume) is owned by a knob (`level_pot`) so blocks cannot write it; the CTRL tab edits it directly.
- **`fez_round`** rounds halves up like JavaScript's Math.round (C's round() rounds halves away from zero, which differs for negative halves).
- **Verification**: the early work was checked headless (scripted desk tests under UBSan, pictures of the screens, the app run on SDL's dummy drivers). Jon has since run the desktop app on macOS and on a Linux amd64 laptop, so the SDL key and audio code in `desk/main.c` (mute fade, scancode piano, focus loss, recording) has been used for real on those two. Still untested: the Raspberry Pi, any ARM build, and the handheld. The sound is judged by ear, not by test.

## The manual

`make manual` builds one page, `docs/manual.html`, in the app's colours (`FEZ_PALETTE` is written into the CSS, so there is one definition). The word reference comes from `core/words.c`, the register reference from `NAME_TABLE`, `HELP_TABLE`, `PARAM_TABLE` and `REG_GROUPS` (in `core/regview.c`, shared with the CTRL tab), so they cannot drift. Chapters are hand-written fragments in `docs/chapters/`; inside one, `<pre class="fez">` holds FEZ source as plain text, which the generator colours like the editor. Headings are drawn in the pixel font (`FONT5`) as SVG. Chapters 1 (first sound), 2 (how it fits together: the sound path and the control path, as two flow diagrams drawn as inline SVG, in the Economist chart manner) 3 (the language), 4 (the voice), 5 (control), 6 (devices), 7 (space), 8 (playing), 9 (handheld) and 10 (patches: using, the file format, making your own) and 11 (the example patches, annotated) are written, so all eleven chapters exist as of 25 Nov 2026. Element ids must be unique across the page (the language chapter's registers section is `language-registers` because the reference owns `registers`); the two references are done. The diagrams were laid out by a throwaway script and are now plain SVG in `docs/chapters/02_overview.html`: edit them there. Jargon rule: define a term on first use in plain words (Jon asked for 8.8 fixed point to be explained; saturating arithmetic is explained; slots, tokens, tick, fault explained; Q15 is described as 'fractions where 32768 is 1.0'). Decisions: see the memory note on the manual plan. Every `<pre class="fez">` example is compiled when the manual is built (an invalid one stops `make manual`). Screenshots: `tools/shots.sh` (macOS `sips`) remakes `docs/shots/*.png` from `deskshot` and `padshot`; a chapter uses `<img src="shots/NAME.png">` and the generator embeds the bytes, so the page stays one file (a missing picture stops the build). Not yet done: running the examples, the word table feeding the editor's palette.
